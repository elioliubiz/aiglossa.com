# AIGLOSSA 视觉系统

> 状态：2026-11-02 方向已确认；Food 为首个正式落地试点。

## 目标

AIGLOSSA 的网站、工具和 Scholan 使用同一套视觉语言，但不强迫不同业务拥有相同的页面形态或主色。统一发生在排版、间距、材质、控件、状态和交互；产品色只负责识别与氛围。

视觉方向：浅淡而有颜色的环境背景、鲜明的功能色、克制的半透明层次与彩色阴影。暗色模式必须重新设计表面与对比关系，不能把浅色页面机械反相。

## 设计边界

- 共享：字体尺度、间距、8px 以内的常规圆角、边框、阴影、按钮、输入框、弹窗、账户区、焦点态、加载态和语义状态色。
- 独立：产品信息架构、业务表单、播放器、分析报告、阅读器及业务特有的媒体表现。
- 平台外壳保持安静；产品色主要用于主操作、选中态、局部氛围、识别标记和数据重点，不能铺满所有表面。
- 成功、提醒、危险等颜色表示固定语义，不跟随产品主题改变。
- 图片和生成素材必须承担内容或品牌识别作用，不添加无功能的装饰图。现有素材不足时可以生成专用素材，但要同时检查裁切、暗色模式和移动端效果。

| Image | `#EF6548` | `#315BD8` | `#F2CF3F` | 颜料、摄影、印刷和视觉编辑 |

## 明暗主题

- 默认跟随 `prefers-color-scheme`，用户选择后写入本地偏好并优先使用。
- 浅色背景不能是空白纯白画布；使用低对比色域建立环境感，内容表面保持清晰。
- 浅色主题以冷白和中性表面为主体，可在环境背景中同时加入极淡的蓝、青、粉、黄等流光；产品主色只在关键组件与状态上提高饱和度，禁止把整页染成单一产品色。
- “有颜色”不等于“大面积铺主题色”。鲜明感来自中性环境与少量高饱和重点之间的对比，而不是持续提高背景色浓度。
- 暗色使用带少量色相的深层表面，不使用纯黑；层级主要依靠明度、边框和局部光色，不依赖更重的黑色阴影。
- 正文、次要文字、边框和禁用态都必须分别定义明暗 token，禁止靠透明黑白临时推算全部状态。
- 页面必须在桌面与移动端分别检查浅色、暗色、RTL、长文本和减少动态效果设置。

## 组件规则

- 页面区块不做漂浮卡片；卡片只用于重复项目、弹窗或确实需要边界的工具区域。
- 常规控件圆角不超过 8px；媒体、模态窗口和大型业务容器可按内容适当增加。
- 熟悉的操作优先使用图标按钮并提供可访问名称；命令按钮才使用文字。
- 不嵌套装饰卡片，不使用无意义的渐变球、光斑或大面积单色渐变。
- 登录、账户和余额属于 Platform 层，跨站保持结构与材质一致；它们可以带少量当前产品色，但不能变成另一套页面。
- 固定格式内容要有稳定尺寸或比例，加载、长文案和状态变化不能造成布局跳动。

## 产品外壳与页面层级

- 各产品顶栏的品牌文字统一为 `AIGLOSSA`；产品身份由图标、产品色、页面标题和内容表达。不要在顶栏追加 `FOOD`、`SKIN` 等长后缀，以免移动端账户区和操作按钮被挤压。面包屑、页脚和页面标题仍可使用完整产品名表示层级。
- 桌面端的历史页、结果页使用面包屑表达位置；移动端和 PWA 在顶栏保留返回图标。公开分享页是独立入口，不显示返回按钮。
- 历史、结果、分享必须是拥有独立 URL 的页面，不能用首页内嵌视图伪装页面跳转。站内进入时遵循浏览器历史；直接打开深层链接时，页面内返回以产品首页兜底。
- 产品之间共享视觉规则和稳定 token，不直接继承另一个产品的整份业务 CSS。Food、Skin 等页面可以拥有相似结构，但模板、脚本和产品样式仍分别维护，避免一个产品改版意外改变另一个产品。

## 加载与动态效果

- 异步历史、结果和分享内容使用与最终布局一致的骨架屏，保留最终页面的大致尺寸，避免居中转圈造成大片空白和加载完成后的布局跳变。
- 数据加载完成只做一次短淡入；报告正文和长列表不逐项播放进入动画。首页的叙述区可以在首次进入视口时轻微淡入上移，但不能延迟核心操作。
- 按钮、菜单、弹窗等状态变化以约 `120–220ms` 的短过渡为主；骨架 shimmer 和内容进入动画不得抢占阅读注意力。
- 所有非必要动画必须响应 `prefers-reduced-motion: reduce`，关闭位移、滚动渐入和 shimmer；内容在脚本失败或动画 API 不可用时仍应直接可见。

## 排版与控件细节

- 每个页面只建立有限的字重层级：正文常规、标签中等、标题半粗、主标题展示字重。不要让按钮、正文、卡片标题和页面标题同时使用接近的粗体。
- 中文主标题应避免机械使用最粗字重；通过字号、行高和空间建立重点。正文与说明文字优先保证清晰度，不能靠大量小于 12px 的灰字制造“精致感”。
- 数据使用稳定的数字宽度；数值、单位和参考比例分别建立层级，不用条形长度替代真实数值，也不能把每日参考比例表现成健康评分。
- 所有可交互元素必须能从静态页面中被识别：语言选择、登录、主题切换、菜单等应有明确的边界、点击区域、状态或下拉指示，不能只靠文字颜色暗示可点击。
- 同一控制层级使用一致的高度、圆角、边框和字重；图标可以更小，但点击区域在触屏上不得小于 44px。

## 信息密度与页面质感

- 先按产品任务组织内容，再决定视觉形式。营销式介绍、实际操作、结果预览和解释内容的密度可以不同，但不能用同一种空卡片重复铺满页面。
- 信息区可以紧凑，叙述区应留出呼吸空间；留白必须服务于分组、聚焦或节奏，不能只是因为内容不足而把少量文字强行拉伸到固定高度。
- 展示产品能力时优先呈现真实输出形态，例如状态、数据、摘要、媒体或可交互预览，而不是只写“我们能做什么”。
- 增加内容必须能回答用户问题、解释结果或预示下一步；不为了填满空间添加泛化卖点、虚构指标或装饰性模块。
- 同一区域建立明确的主次关系：一个主要视觉锚点，若干支持信息；避免所有标题、边框和色块拥有相同权重。
- 评审时分别检查信息完整度、视觉层级、间距节奏、长文本、无数据状态和响应式重排，不能只确认颜色与组件是否一致。

以上原则参考社区开源项目 `nextlevelbuilder/ui-ux-pro-max-skill` 的产品类型、密度、响应式与交付检查方法，并按 AIGLOSSA 的实际业务边界重新整理；不直接套用其预设风格或组件模板。

## 落地与验证

1. Food 已完成首轮试点；后续产品沿用已确认的视觉规则，但必须重新核对自己的真实业务内容与页面层级。
2. 验证首页、真实业务状态、历史页、独立结果页、分享页、账户入口、弹窗、移动端和暗色模式后，再认为一个产品迁移完成。
3. 依次扩展到 Skin、Platform/账户、Tools 入口、Music、Image、Scholan；业务页面不因视觉统一而强行共用模板。
4. 修改资源后 bump 对应资源版本与 PWA cache，运行 `python3 tools/build.py` 和 `python3 tools/verify.py`。
5. 先在本地和 staging 验证，用户确认后才能进入生产。

本地色彩原型位于 `prototypes/visual-system.html`，只用于设计评审，不进入生产站点或 sitemap。
